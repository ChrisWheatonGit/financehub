# v1.4 Authenticated household development foundation

## What is implemented
- Better Auth email/password sessions with Prisma adapter; **development use only**.
- PostgreSQL/Prisma schema for users, sessions, households, membership, invitations, financial accounts, and ledger transactions.
- API routes for create/list household; list its members; generate one-use 24-hour invite token; accept invite for authenticated matching email; list/create household ledger transactions with ownership validation and exact-cent split validation.
- Interactive test page: `/household`. Main dashboard and financial modules remain isolated **browser-only demo**; they are NOT secured or synchronized.

## Local Windows setup (development only)
1. Create branch; copy bundle source into repository preserving `.git`, local `.env`.
2. `npm install`
3. Add these values to `.env`: `POSTGRES_USER=financehub`, `POSTGRES_DB=financehub`, `POSTGRES_PASSWORD=<long random password>`, `DATABASE_URL=postgresql://financehub:<URL-ENCODED-PASSWORD>@localhost:5432/financehub`, `BETTER_AUTH_SECRET=<at least 32 random bytes>`, `BETTER_AUTH_URL=http://localhost:3000`.
4. Start PostgreSQL for development: `docker compose -f docker-compose.dev.yml up -d`.
5. `npx prisma generate`, then `npx prisma migrate dev --name init_household_auth` (on a **new empty disposable** development database). Review generated migration SQL; do not use db push in production.
6. `npm run test:household`, `npm run build`, `npm run dev`. Visit `http://localhost:3000/household`.
7. For two-user tests, use two separate browser profiles; register test accounts, create household, generate invitation, sign into second account, accept token, verify both see members.
8. Confirm an unrelated third user receives HTTP 404 on `/api/households/{householdId}` and `/api/households/{householdId}/transactions`.

## Security limitations / production blockers
- NO confirmed email verification, password reset, MFA, account lockout policy, request rate limiting, notification delivery, or independent penetration test.
- No enforced PostgreSQL RLS yet; tenant checks are at the application API layer only. Privileged DB credentials must never reach browsers. RLS must be implemented and demonstrated in integration tests before production.
- `/household` is a test interface; signed-out visitors see only the login form, protected API routes enforce sessions.
- Invitations are returned as tokens for **local testing only**; never use this workflow on the public Internet. They are stored hashed, scoped by recipient email, and expire within 24h. Production requires verified email + delivery and anti-abuse safeguards.
- Existing browser-only financial data is not migrated or protected by these APIs. NEVER enter real financial data.
- No cross-tenant integration tests have been executed here; add tests with seeded disposable PostgreSQL and two separate authenticated sessions before broad use.
- Better Auth and Prisma version compatibility must be validated with `npm run build` and manual local tests.
- A proposed later phase includes authenticated household UI, account reconciliation and migrations of demo transactions.
